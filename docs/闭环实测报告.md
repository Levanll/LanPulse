## 零、补测：五个此前未验证的动作

v1.1.0 的闭环只覆盖 DNS 类动作，报告原第五节列出的"未证明"清单里点名了
`proxy.reset`、`firewall.ensure_enabled`、`tcp.autotuning`、`hosts.clean_bad_lines`
四项。本版按风险从低到高全部补测完成，**4/4 通过**。

### 0.1 为什么这四个动作需要单独设计测试

它们与 DNS 类动作有一个本质差别：**只在"需要修"时才会动手**。

| 动作 | 本机测试前状态 | 直接执行会怎样 |
|---|---|---|
| `proxy.reset` | 已是直连（ProxyEnable=0） | 仍然写 ProxyEnable=0，但无实际变化 |
| `firewall.ensure_enabled` | 三个 profile 已全关 | 真实执行，可验证 |
| `tcp.autotuning` | 已是 normal | 仍写 normal，读回相同 |
| `hosts.clean_bad_lines` | 无可疑记录 | 返回 SKIPPED，文件不动 |

若直接跑，"回滚"没有任何东西可回滚，验证是空的。因此测试分两段：
**先构造出待修状态，再执行修复**，这样才能真正验证"改得对、退得干净"。

### 0.2 关键设计：备份备份的是"构造后的故障态"

这是个容易搞错的点。动作的 `backup()` 在"构造故障态之后"才运行，所以它
备份的是造出来的故障，回滚只能回到**构造态**，回不到更早的原始态。

这**不是缺陷**——真实用户遇到的本来就是故障态，备份它才是正确的。
正确的验收判据因此是：

```
快照D（回滚后） == 快照B（构造态）     ← 验证"修复被撤销干净"
快照E（复原后） == 快照A（原始态）     ← 额外保障，让本机回到测试前
```

两个都比对，前者证明产品能力，后者证明测试本身没有污染本机。

### 0.4b v1.2.1 补测：netbios.disable_public

第一档遗留项。选它先做，理由是验证成本最低而暴露过的风险最高：
它只改一个 `NetbiosOptions` DWORD，回滚有两条路径（注册表整项导入 /
原本不存在则删值），而它在界面里是**默认勾选**的动作，却因导入缺陷
从未被真实执行过。

```
✓ netbios.disable_public   applied=True verified=True
  NetbiosOptions: 0（由 DHCP 决定） -> 2（禁用）

五项合计 5/5 通过
测试后本机 NetbiosOptions 回到 0，与快照 A 一致
```

**为它扩展了快照工具**：`tools/snapshot_net.py` 原先不采集 NetBIOS 状态，
这会让该动作无法做机器判决、只能靠人眼比对。现已加入 `_netbios()` 并在
`diff()` 里比对，与其它项同等对待。

### 0.5 本轮发现并修复的缺陷

**缺陷 C：两个修复动作缺少 `platform_win` 导入（真实缺陷，已修）**

`firewall.ensure_enabled` 与 `netbios.disable_public` 的模块顶部都没有
`from .. import platform_win as pw`，而 `apply()` 内部调用了 `pw.now()`。

- **为什么之前没发现**：单测不执行动作，`dry_run=True` 也不走 `apply()`——
  两者都覆盖不到这一行。只有真实提权执行时才暴露。
- **实测表现**：执行到 `apply()` 立刻抛
  `NameError: name 'pw' is not defined`，动作记为 FAILED。
- **影响面**：`firewall.ensure_enabled` 与 `netbios.disable_public` 两个动作
  在真实环境下**必然失败**。后者在 UI 里是默认勾选项，影响更大。
- **修复**：两个模块补齐导入。
- **防复发**：新增 `tests/test_repair_contracts.py`，用静态 AST 扫描
  "使用了但未导入的模块级别名"，并额外校验 action_ids 与 REGISTRY 一一对应、
  回滚分派覆盖全部 kind。已用临时移除导入的方式验证该测试确实会失败。

**缺陷 D：测试脚本自身的判定逻辑错误（工具缺陷，已修）**

初版把"构造态与原始态无差异"当失败处理。但防火墙本机原本就全关，构造
步骤不产生差异是正常的，动作依然真实执行了 `netsh` 并置为 ON。已改为：
- apply 是否成功 → 看动作状态与 verify，而非快照差异
- 构造是否生效 → 无差异只记说明，不算失败

## 一、为什么要做这次测试

此前所有修复引擎验证都停留在 `dry_run=True`——只证明"备份链路是通的"，
**没有证明"真实修改能成功"和"回滚能完整还原"**。

这是一款会直接改写用户系统网络配置的软件，`dry_run` 通过不代表真实链路可用。
本次在有管理员权限的环境下补上了这个缺口。

## 二、测试方法

### 2.1 选择测试动作

| 动作 | 选它的理由 |
|---|---|
| `dns.set_public` | 真实改写网卡 DNS（有明确前后状态），备份记录原服务器列表 + `was_dhcp`，回滚可精确还原 |
| `dns.flush_cache` | 无持久状态，用来验证"无备份项的动作"也能正常进出流程 |

改造成的 DNS 目标选 **Quad9（9.9.9.9 / 149.112.112.112）**，与原本的阿里系
（223.5.5.5 / 223.6.6.6 / 119.29.29.29）差异明显，便于人眼与机器双重识别。

### 2.2 机器判决而非人眼判决

编写了 `tools/snapshot_net.py`，在关键节点抓取并比对 **12 项**状态：

1. 主网卡 DNS 列表
2. hosts 文件 SHA256
3. WinINET `ProxyEnable`
4. WinINET `ProxyServer`
5. WinINET `ProxyOverride`
6. WinINET `AutoConfigURL`
7. WinHTTP 代理
8. TCP `autotuning`
9. TCP `rss`
10. TCP `ecn`
11. 主网卡 MTU
12. 防火墙三个 profile 状态

任一项不同即判定失败。**不依赖"看起来没问题"。**

### 2.3 六个阶段

```
[1] 基线快照
[2] dry-run（验证备份链路；并断言 dry-run 不改动系统）
[3] 真实执行修复
[4] 执行后快照（断言系统确实被改了，否则说明 apply 假成功）
[5] 回滚
[6] 回滚后快照，与基线逐项比对（断言零差异）
```

第 [2] 与 [4] 两个断言是关键：它们把"备份成功"和"真的改成功"分开验证，
防止出现"报告说 applied、实际没变"这类**假成功**。

## 四、过程中发现并修复的缺陷

### 缺陷 A：提权控制台编码导致测试中断（工具缺陷，非产品缺陷）

**现象**：首次提权运行时，脚本在打印 diff 结果时崩溃：

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u05f4'
```

**影响**：测试在第 [4] 步中断，**而系统此刻已被改为 Quad9**——
如果只看"脚本崩了"就结束，用户会留下一个未还原的 DNS 改动。

**处理**：
1. 立即用独立回滚工具 `tools/rollback_session.py` 依据已生成的备份会话还原，
   实测 DNS 与 hosts 均已回到基线；
2. 修复脚本：对控制台输出做 `errors="replace"` 兜底，日志文件始终 UTF-8；
3. 重跑完整流程，得到干净的验收记录。

**这条本身也是有价值的验证**：它证明了**即使主流程崩溃，只要备份已生成，
仍可用独立路径精确还原**。这正是"备份不依赖软件运行时状态"这一设计目标的实证。

### 缺陷 B：独立回滚工具的 `session_path` 属性引用

初版 `rollback_session.py` 调用了 `BackupSession` 不存在的 `session_path` 属性。
已改为使用 `session.path`（该 dataclass 实际字段名）。

## 五、这次测试证明了什么 / 没证明什么

### 已证明

- ✅ 备份在真实修改前生成，且内容足以精确还原（含 `was_dhcp` 判定依据）
- ✅ `apply` 真实生效，不是"报告成功但没变"
- ✅ `verify` 读回校验有效（`verified=True` 与实测状态一致）
- ✅ 回滚能把 12 项状态精确还原，与基线**零差异**
- ✅ 动作作用范围精确，不波及其它配置
- ✅ dry-run 确实不碰系统
- ✅ 主流程崩溃时，仍可用独立路径从备份还原
- ✅ 回滚后网络功能正常

### 未证明（仍需在更多环境验证）

- ⚠️ **已补测 5 项，仍有以下动作未做真实闭环**：
  - `tcp.reset_stack` / `adapter.reset_stack`（需重启才能完全生效）
  - `mtu.optimize`（会改网卡 MTU，需谨慎构造目标值）
  - `adapter.renew_dhcp`（会短暂断网 3-10 秒）
- ⚠️ **只测了单动作场景**，未测大规模批量（10+ 动作）下的异常中断与部分失败回滚
- ⚠️ 未测**回滚本身失败**时的兜底路径（例如备份文件被外部删除/损坏）
- ⚠️ 未在 Windows 10 上验证（本机为 Windows 11）

v1.1.0 曾建议按风险从低到高补测
`proxy.reset` → `firewall.ensure_enabled` → `tcp.autotuning` → `hosts.clean_bad_lines`。
**v1.2.0 已全部完成**，`netbios.disable_public` 于 v1.2.1 补测完成（见本文第零节）。

## 六、复现方式

```powershell
# 前提：以管理员身份运行 PowerShell
cd <项目根>

# v1.1.0 的 DNS 类闭环（会真实修改网卡 DNS，结束时自动回滚）
.\.venv\Scripts\python.exe tools\closed_loop_test.py

# v1.2.0 的四动作闭环（会临时构造故障态再修复，结束时自动复原）
.\.venv\Scripts\python.exe tools\closed_loop_v12.py

# 若主流程意外中断，用备份独立还原：
.\.venv\Scripts\python.exe tools\rollback_session.py           # 列出会话

.\.venv\Scripts\python.exe tools\rollback_session.py <id>       # 执行

# 任意时刻手动比对状态
.\.venv\Scripts\python.exe tools\snapshot_net.py a.json
.\.venv\Scripts\python.exe tools\snapshot_net.py b.json
.\.venv\Scripts\python.exe tools\snapshot_net.py --diff a.json b.json
```

- v1.1.0：`verify/` 下的 `10_before.json` / `30_after_apply.json` /
  `40_after_rollback.json` / `closed_loop.log`
- v1.2.0：`verify/` 下每个动作四份快照
  （`*_A_original` / `*_B_fabricated` / `*_C_applied` / `*_D_rolledback` /
  `*_E_restored`）+ `closed_loop_v12.log` + `closed_loop_v12_summary.json`

## 七、结论

**核心安全承诺成立**：先备份、后修改、可回滚，且回滚是精确的、经过实测验证的。

这次测试也暴露了一个此前只在理论上讨论的风险——**流程中断时可能留下未还原的配置**。
实际表现是：备份已经落盘，因此可以用完全独立于主程序的路径还原。
这验证了备份层"不依赖软件运行时状态"的设计是对的。
