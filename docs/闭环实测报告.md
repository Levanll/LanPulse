## 一、为什么要做这次测试

此前所有修复引擎验证都停留在 `dry_run=True`——只证明"备份链路是通的"，
**没有证明"真实修改能成功"和"回滚能完整还原"**。

这是一款会直接改写用户系统网络配置的软件，`dry_run` 通过不代表真实链路可用。
本次在有管理员权限的环境下补上了这个缺口。

## 二、测试方法

### 2.1 选择测试动作

| 动作 | 选它的理由 |
|---|---|
| `dns.set_public` | 真实改写网卡 DNS（有明确前后状态），备份记录原服务器列表 + `was_dhcp`，回滚可精确还原 |
| `dns.flush_cache` | 无持久状态，用来验证"无备份项的动作"也能正常进出流程 |

改造成的 DNS 目标选 **Quad9（9.9.9.9 / 149.112.112.112）**，与原本的阿里系
（223.5.5.5 / 223.6.6.6 / 119.29.29.29）差异明显，便于人眼与机器双重识别。

### 2.2 机器判决而非人眼判决

编写了 `tools/snapshot_net.py`，在关键节点抓取并比对 **12 项**状态：

1. 主网卡 DNS 列表
2. hosts 文件 SHA256
3. WinINET `ProxyEnable`
4. WinINET `ProxyServer`
5. WinINET `ProxyOverride`
6. WinINET `AutoConfigURL`
7. WinHTTP 代理
8. TCP `autotuning`
9. TCP `rss`
10. TCP `ecn`
11. 主网卡 MTU
12. 防火墙三个 profile 状态

任一项不同即判定失败。**不依赖"看起来没问题"。**

### 2.3 六个阶段

```
[1] 基线快照
[2] dry-run（验证备份链路；并断言 dry-run 不改动系统）
[3] 真实执行修复
[4] 执行后快照（断言系统确实被改了，否则说明 apply 假成功）
[5] 回滚
[6] 回滚后快照，与基线逐项比对（断言零差异）
```

第 [2] 与 [4] 两个断言是关键：它们把"备份成功"和"真的改成功"分开验证，
防止出现"报告说 applied、实际没变"这类**假成功**。

## 四、过程中发现并修复的缺陷

### 缺陷 A：提权控制台编码导致测试中断（工具缺陷，非产品缺陷）

**现象**：首次提权运行时，脚本在打印 diff 结果时崩溃：

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u05f4'
```

**影响**：测试在第 [4] 步中断，**而系统此刻已被改为 Quad9**——
如果只看"脚本崩了"就结束，用户会留下一个未还原的 DNS 改动。

**处理**：
1. 立即用独立回滚工具 `tools/rollback_session.py` 依据已生成的备份会话还原，
   实测 DNS 与 hosts 均已回到基线；
2. 修复脚本：对控制台输出做 `errors="replace"` 兜底，日志文件始终 UTF-8；
3. 重跑完整流程，得到干净的验收记录。

**这条本身也是有价值的验证**：它证明了**即使主流程崩溃，只要备份已生成，
仍可用独立路径精确还原**。这正是"备份不依赖软件运行时状态"这一设计目标的实证。

### 缺陷 B：独立回滚工具的 `session_path` 属性引用

初版 `rollback_session.py` 调用了 `BackupSession` 不存在的 `session_path` 属性。
已改为使用 `session.path`（该 dataclass 实际字段名）。

## 五、这次测试证明了什么 / 没证明什么

### 已证明

- ✅ 备份在真实修改前生成，且内容足以精确还原（含 `was_dhcp` 判定依据）
- ✅ `apply` 真实生效，不是"报告成功但没变"
- ✅ `verify` 读回校验有效（`verified=True` 与实测状态一致）
- ✅ 回滚能把 12 项状态精确还原，与基线**零差异**
- ✅ 动作作用范围精确，不波及其它配置
- ✅ dry-run 确实不碰系统
- ✅ 主流程崩溃时，仍可用独立路径从备份还原
- ✅ 回滚后网络功能正常

### 未证明（仍需在更多环境验证）

- ⚠️ **只测了 DNS 类动作**。`dns.set_public` / `dns.flush_cache` 是注册表与命令型修改，
  逻辑最直接。以下类型尚未做真实闭环：
  - 注册表型：`proxy.reset`、`tcp.reset_stack`、`netbios.disable_public`
  - 文件型：`hosts.clean_bad_lines`（会改写 hosts，风险最高）
  - 网络配置型：`mtu.optimize`、`adapter.renew_dhcp`（会导致短暂断网）
  - 系统服务型：`firewall.ensure_enabled`
- ⚠️ **只测了单动作与两动作并发的简单场景**，未测大规模批量（10+ 动作）下的
  异常中断与部分失败回滚
- ⚠️ 未测**回滚本身失败**时的兜底路径（例如备份文件被外部删除/损坏）
- ⚠️ 未在 Windows 10 上验证（本机为 Windows 11）

建议后续按风险从低到高补测：`proxy.reset` → `firewall.ensure_enabled` →
`tcp.autotuning` → `hosts.clean_bad_lines`（最后测，需先准备一份带可疑记录的 hosts）。

## 六、复现方式

```powershell
# 前提：以管理员身份运行 PowerShell
cd <项目根>

# 完整闭环（会真实修改网卡 DNS，结束时自动回滚）
.\.venv\Scripts\python.exe tools\closed_loop_test.py

# 若主流程意外中断，用备份独立还原：
.\.venv\Scripts\python.exe tools\rollback_session.py           # 列出会话
.\.venv\Scripts\python.exe tools\rollback_session.py <id> --dry # 预览
.\.venv\Scripts\python.exe tools\rollback_session.py <id>       # 执行

# 任意时刻手动比对状态
.\.venv\Scripts\python.exe tools\snapshot_net.py a.json
.\.venv\Scripts\python.exe tools\snapshot_net.py b.json
.\.venv\Scripts\python.exe tools\snapshot_net.py --diff a.json b.json
```

产物：`verify/` 目录下的 `10_before.json` / `30_after_apply.json` /
`40_after_rollback.json` / `closed_loop.log`。

## 七、结论

**核心安全承诺成立**：先备份、后修改、可回滚，且回滚是精确的、经过实测验证的。

这次测试也暴露了一个此前只在理论上讨论的风险——**流程中断时可能留下未还原的配置**。
实际表现是：备份已经落盘，因此可以用完全独立于主程序的路径还原。
这验证了备份层"不依赖软件运行时状态"的设计是对的。
