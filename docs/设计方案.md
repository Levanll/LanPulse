# LanPulse 网络体检与一键修复 —— 设计方案与实现说明

> 版本 v1.0.0　｜　平台 Windows 10 (1809+) / Windows 11 / Server 2019+
> 全部检测与修复在本机完成，不联网上传任何数据。支持中文 / English 双语。
> 唯一的对外请求除检测探测外，是一个**默认关闭、需用户同意**的版本号查询
> （`GET latest.json`），只读取版本信息，不携带任何本机数据。

---

## 一、需求到设计的映射

用户要的是"普通用户双击就能解决网络问题"的工具。这句话拆开是三件事，缺一个就变成"极客玩具"：

| 用户诉求 | 设计回应 | 落地位置 |
|---|---|---|
| 不知道哪里出问题 | 自动体检 → 一句话结论 + 健康分 | 仪表盘、诊断详情 |
| 不知道怎么修 | 检测结果驱动生成修复清单，逐项可勾选 | 一键修复页 |
| 不敢修（怕改坏） | 先备份后修改、可回滚、可演练、全过程留痕 | 备份与回滚页、审计流水 |

"科技感"不是加动效，而是让**状态可被一眼读懂**：健康度环形仪表的颜色即结论。

## 二、技术选型

| 维度 | 选择 | 理由 |
|---|---|---|
| 语言 | Python 3.12 | 系统调用以 ctypes / 标准库即可完成，无编译依赖 |
| UI 框架 | PySide6 6.8（Qt 6, LGPL） | 自绘能力强（QPainter 画渐变弧/发光）、高 DPI 友好、商用授权清晰 |
| 打包 | PyInstaller 6.22，**单目录模式** | 单文件每次启动要解压 Qt 运行时，冷启动 3-6 秒且杀软误报率高 |
| 安装包 | Inno Setup 6.7 | 支持中英双语向导、用户级安装免管理员、卸载可保留数据 |
| 系统能力 | `netsh` / `ipconfig` / `route` / `reg` / WMI-CIM / `winreg` / `dnsapi!DnsQuery_W` / `wininet` | 全部 Windows 原生，无第三方驱动或服务 |
| 数据格式 | JSON（报告/备份/设置）、HTML（可视化报告） | 无数据库，用户可直接用记事本查看与手工还原 |
| 国际化 | 自研扁平 dict + Qt 信号 | 只有两种语言约 1200 条文案；Qt .ts/.qm 需 lrelease 编译，改文案要重走流程 |

## 三、功能模块划分

```
LanPulse
├── 检测引擎 core/checks/          14 个独立可复用检测单元
│   ├── adapter / ip / gateway / dns_server / dns_resolve
│   ├── hosts / proxy / tcp / mtu / firewall / connectivity
│
├── 修复引擎 core/repair/          15 个原子动作 + 事务编排
│   ├── engine      规划 / 预览 / 执行 / 回滚
│   ├── base        动作协议 + 注册表（含可用性探针）
│   └── rollback    按 kind 分派的唯一回滚实现
│
├── 安全中间层 core/backup.py       备份与回滚的唯一入口
├── 跨区域层 core/region.py         12 套区域剖面 + 网络环境识别
├── 设置层 core/settings.py         持久化 + 变更广播
├── 国际化 core/i18n.py             运行时切换 + 缺失可见
│            core/i18n_args.py      参数内 i18n key 解析
│
└── 表现层 app/ui/                  9 个页面 + 自绘控件
```

### 检测单元的可扩展性

新增检测维度只需两步：写一个带 `check_id / title / category` 与 `run(ctx)` 的类，在 `core/registry.py` 的 `load_checks()` 登记。UI 表格、报告、健康分自动包含它。

每项由 `run_check()` 统一包裹：计时、异常隔离。单项崩溃转为 `SKIP` 并记录原始异常，**不会让整轮体检失败**。

## 四、跨区域自适应（本版新增，核心能力）

### 4.1 问题

检测必须有"往哪里打"的目标。硬编码目标只在单一地区成立：

- 在国内拿 `8.8.8.8` 当基准 → 可能慢到超时，误判"外网不通"
- 在欧洲拿 `223.5.5.5` 当基准 → 直接不通，全项报错
- 用国内的 150ms 阈值判欧美 → 正常的跨国链路被判"高延迟"

### 4.2 设计：探测集与判定逻辑分离

```
判定逻辑（通用）          探测集（地域相关）
延迟分档 / 丢包率    ←    来自 RegionProfile
延迟阈值 / 握手阈值  ←    来自 RegionProfile
```

12 套剖面（`core/region.py`）。v1.2.0 之前只有 CN / Global / APAC 三套，
其中 Global 同时覆盖欧美、APAC 同时覆盖日韩与东南亚——这两组区域网络环境差异很大，
用同一套探测目标必然误判，因此按主要国家/地区细分：

| key | 区域 | 解析域名示例 | ping / MTU 目标 | 推荐 DNS（首位） | RTT / 解析正常阈值 |
|---|---|---|---|---|---|
| `cn` | 中国大陆 | 百度/腾讯/淘宝/B站 | 223.5.5.5 | 阿里+腾讯 | 120 / 150 ms |
| `hk` | 中国香港 | Google/Cloudflare/Yahoo HK | 1.1.1.1 | Cloudflare+Google | 110 / 140 ms |
| `mo` | 中国澳门 | Google/Cloudflare/gov.mo | 1.1.1.1 | Cloudflare+Google | 120 / 150 ms |
| `tw` | 中国台湾 | Google/Cloudflare/PChome | 1.1.1.1 | Cloudflare+Google | 110 / 140 ms |
| `jp` | 日本 | Google/Yahoo日本/乐天 | 1.1.1.1 | 日本本地 | 110 / 140 ms |
| `kr` | 韩国 | Google/Naver/Daum | 1.1.1.1 | 韩国本地 | 110 / 140 ms |
| `sg` | 新加坡/东南亚 | Google/Straits Times/Shopee | 1.1.1.1 | Cloudflare+Google | 130 / 160 ms |
| `in` | 印度/南亚 | Google/Flipkart/Rediff | 1.1.1.1 | Cloudflare+Google | 180 / 220 ms |
| `au` | 澳大利亚/新西兰 | Google/ABC/Gumtree | 1.1.1.1 | Cloudflare+Google | 170 / 200 ms |
| `na` | 北美 | Google/Wikipedia/GitHub | 1.1.1.1 | Cloudflare+Google | 130 / 160 ms |
| `eu` | 欧洲 | Google/Wikipedia/Heise | 1.1.1.1 | 欧盟公共（GDPR） | 130 / 170 ms |
| `other` | 其他 | Google/Wikipedia/GitHub | 1.1.1.1 | Cloudflare+Google | 190 / 230 ms |

`other` 承接所有识别不出的网络，阈值取全部剖面里最宽松的一档——**识别不出的用户
不应该被误报成网络故障**。旧版设置里存的 `global` / `apac` 由 `normalize_region()`
映射到 `other`，升级后不会出现空白选项。

### 4.3 自动识别（全本地，不请求任何定位 API）

判定顺序，先强后弱：

1. **延迟打分**：TCP 握手测"中国锚点 223.5.5.5"与"全球 anycast"（1.1.1.1 / 8.8.8.8 / 9.9.9.9，
   取到第一个可用值即停）。差距 > 60ms 才采信。
   > 这一步**只能判定"在不在中国大陆"**。东亚各区（日韩台新）彼此只差十几毫秒，
   > 且全球 anycast 处处就近接入，测出来的差距没有区分度。硬用它细分国家必然判错。
2. **时区**：读 `TimeZoneKeyName`（如 `China Standard Time`），可精确到国家。
   > 踩坑：`StandardName` 在中文系统上是 `@tzres.dll,-572` 这种资源引用，不含任何地理信息，用它做匹配永远失败。
   > 已知局限：大陆、香港、澳门共用 `China Standard Time`，港澳完全依赖系统地区码判定。
3. **系统语言**：`zh-CN → cn`、`zh-HK → hk`、`zh-MO → mo`、`zh-TW → tw`、`ja → jp`、
   `ko → kr`、`en-AU → au`、`en-GB → eu`、欧洲各语种 → `eu`，其余 → `other`。

用户可在设置里固定区域，覆盖自动识别。

### 4.4 网络环境识别

除了地域，不同**接入类型**也要区别对待：

| 环境 | 检测 | 处理 |
|---|---|---|
| 强制门户（酒店/机场/校园网） | 请求 `connectivitycheck.gstatic.com/generate_204`，非 204 即被拦截 | 单独提示"需网页登录"，不误报为 DNS 故障 |
| VPN 活动 | 虚拟网卡 up 且有网关 | VPN 网卡不参与 DNS/MTU 优化决策，避免破坏既有配置 |
| 仅 IPv6 | 有全局 v6 无 v4 | 跳过 IPv4 专属探测，避免全部失败 |
| 慢速网络 | 用户设置超时倍数 | 所有命令与探测超时统一放大 |

## 五、国际化设计（本版新增）

### 5.1 三条硬规则

1. **缺失 key 必须显式可见**：`t()` 找不到时返回 `⟦key⟧` 而不是静默回退英文——否则漏翻的界面看起来像正常的英文界面，永远发现不了。
2. **两语言 key 集合必须完全一致**，测试逐 key 比对。
3. **占位符必须一致**：同一 key 在两种语言里的 `{placeholder}` 集合必须相同，否则 `.format()` 会错位或抛异常。

### 5.2 最关键的设计难点：后台线程翻译

体检在**后台线程**执行。最初的实现是检测时直接 `t("key")` 翻成当前语言存进结果——于是用户切换语言后，**旧结果冻结在旧语言**。

修正方案：**结果存 key + 参数，渲染时翻译**。

```python
@dataclass
class CheckResult:
    summary: str = ""                    # 已翻译（fallback）
    summary_key: str = ""                # 用于重译
    summary_args: dict[str, Any] = {}    # 参数，可能内含 i18n key
```

渲染层 `tr_result_summary()` 优先用 `summary_key` + `summary_args` 现翻，保证切换语言立即跟随。

### 5.3 嵌套值的语言问题

`{mode}` 的取值是"静态"/`Static`，`{grade}` 是"优秀"/`Excellent`，`{head}` 是一串"IP（归属名）"。

若检测时先把它们译成中文再塞进参数，英文界面会出现：

```
DNS configuration is healthy (手动指定): 223.5.5.5（阿里公共 DNS）
```

解决：**参数里传 key 而非译文**，由 `core/i18n_args.resolve_args()` 统一解析，支持三种形态：

| 形态 | 例 | 处理 |
|---|---|---|
| 普通值 | `{"ip": "1.2.3.4"}` | 原样传递 |
| key | `{"mode": "value.static"}` | 翻译 |
| 聚合片段 | `{"head_parts": [{"key":..., "args":...}]}` | 逐个翻译后按分隔符拼接 |

> 踩坑：UI 层曾有一份复制粘贴的解析逻辑，与 core 版逐渐分叉，导致 `profiles_parts` 只在一边支持，界面上出现未填充的 `{profiles}`。现在只保留一个实现。

### 5.4 已知限制（如实说明）

**切换语言后，已完成体检的"详细说明"保持原语言。**

原因：详情文案含大量动态实测数值（IP、网关、耗时、MTU 差值），用固定模板难以完整表达；把它们全部结构化需要重写每个检测项的产出逻辑，收益不足以抵消引入新缺陷的风险。

处理：`summary`（一句结论）与全部界面文字已能跟随切换；详情需重新体检。已在 README 与使用说明中如实标注。

## 六、安全机制设计（最高优先级）

### 6.1 三道防线

```
防线 1  权限层：不索要管理员权限也能体检；
        需要提权的动作在 UI 上先拦截，避免"点了没反应"
   ↓
防线 2  事务层：所有修改前必须先备份，备份失败则整轮不执行
   ↓
防线 3  校验层：每条动作执行后立即读回验证；回滚前校验备份完整性
```

### 6.2 备份结构（用户可读、可手工还原）

```
%LOCALAPPDATA%\LanPulse\backups\<时间戳>_<会话id>\
├── manifest.json          会话索引（人可读 JSON）
├── files/hosts.bak        HOSTS 原文（字节级快照 + sha256）
├── reg/reg_tcpip.reg      reg export 导出（可双击导入）
└── state/dns_{GUID}.json  结构化状态（DNS 列表 / was_dhcp / MTU 值等）
```

关键点：

- **备份"恢复所需的全部状态"而非差异**。DNS 备份必须记录 `was_dhcp`——原本是 DHCP 与原本是静态列表，回滚命令完全不同。
- **能在软件外还原**。`.reg` 双击导入，`hosts.bak` 直接复制。
- **manifest 记录 sha256**，回滚前比对，不一致则拒绝覆盖。

### 6.3 执行流程（严格顺序）

```
1. begin()            创建备份会话目录
2. 逐条 backup()      任一失败 → 立即中止，不执行任何 apply
3. store.save()       备份清单落盘（此后即使崩溃也能回滚）
4. 逐条 apply()       单条失败标记 FAILED，继续执行后续
5. 逐条 verify()      读回校验，写入 ActionResult.verified
6. 报告 partial=True  若有失败，明确提示"建议回滚本次会话"
```

**为什么备份失败必须整轮中止**：半套备份意味着一半配置无法恢复，比"什么都不做"更危险。

**为什么 apply 失败要继续**：各动作操作不同对象（DNS/代理/协议栈），一项失败不应牵连其它。

### 6.4 UI 上的安全表达

| 措施 | 位置 |
|---|---|
| 高危动作默认**不勾选** | 修复页（`default_selected=False`，有单元测试锁定） |
| 每项显示 `before → after` | 修复页每行，`preview()` 现读现取 |
| 执行前二次确认弹窗（列清单 + 备份路径 + 高风险提示） | 修复页 |
| 「先演练」：走完整备份流程但不动系统 | 修复页 |
| 逐条三阶段状态（备份/执行/校验） | 修复页实时刷新 |
| 操作审计流水（可导出） | 报告与日志页 |
| 修改 HOSTS 需先进"高级编辑"并二次确认 | HOSTS 页 |
| **卸载时询问是否保留备份（默认保留）** | 安装包 |

## 七、核心逻辑实现要点

### 7.1 中文 Windows 的编码处理

`netsh` / `ipconfig` 在中文系统输出 **GBK**，部分环境混用 UTF-8。统一策略：

```python
for enc in ("utf-8-sig", "utf-8"):
    try: return data.decode(enc)
    except UnicodeDecodeError: continue
for enc in ("gbk", "cp936", "mbcs"):
    try: return data.decode(enc)
    except (UnicodeDecodeError, LookupError): continue
return data.decode("utf-8", errors="replace")
```

### 7.2 DNS 真实计时

ctypes 调 `dnsapi!DnsQuery_W`（A 记录、`BYPASS_CACHE`），对区域剖面给的 4 个域名各测一次，单域名 2 秒、整轮 8 秒预算。失败回退 `socket.getaddrinfo` 并在 evidence 标注 `via=getaddrinfo`。

### 7.3 MTU 实测（DF ping 二分）

```
1. 先用 64 字节小包确认目标可达（避免对禁 ICMP 的目标瞎测）
2. 在 [1400, 1473] 二分，ping -f -l <size>
3. 单包无回复重试一次 —— ICMP 随机丢包会被误当成 MTU 上限
4. ≤8 次探测 / ≤8 秒；测不出则只报配置值
```

第三步是实测踩出来的：不加重试时连续三次得到 `1492/1492/1480`，其中 `1480` 会把"差 20 字节"误判成 WARN。

### 7.4 HOSTS 改写的四重防护

```python
1. 行号一致性比对
   lines = text.splitlines(keepends=True)      # 改写用
   analysis = parse_hosts(text)                # 解析用 splitlines()
   if len(lines) != analysis.total_lines: raise
2. 删完重新解析复核，可疑数不为 0 则拒绝写盘
3. 要删行数 > 有效映射数，或删完为空 → 拒绝
4. 先备份 + atomic_write + sha256 校验
```

第 1 条防的是"两个函数分行方式不同导致行号错位，删错行"——会直接毁掉用户文件。

### 7.5 命令返回码不可信

`netsh` 参数非法时**返回码仍为 0**，只在文本里报错：

```
$ netsh int tcp set global heuristics=disabled
'heuristics' is not a valid argument for this command.
$ echo $LASTEXITCODE
0
```

因此所有 netsh 调用必须同时检查返回码**与输出文本**，否则会把"什么都没做"记成"已应用"。

## 九、开发中修复的真实缺陷（均为实测发现）

| # | 缺陷 | 后果 | 修复 |
|---|---|---|---|
| 1 | **备份文件名含冒号被 NTFS 当成交替数据流（ADS）** | `reg:tcpip.reg` 实为文件 `reg` 的隐藏流。目录里只见 0 字节的 `reg`，`isfile()` 仍 True，但 `reg import` 读不到 → **备份"看起来成功"、回滚 100% 失败**。实测 14 项中招 | `safe_name()` 替换非法字符 + 回归测试 |
| 2 | 排除列表误删 `shiboken6.Shiboken` | 打包后 windowed 启动即崩，只弹 "Unhandled exception"，无 traceback | 从排除表移除并注释原因 |
| 3 | `netsh` 参数非法时返回码仍为 0 | 把"什么都没做"记成"已应用" | 同时扫描返回码与输出文本 |
| 4 | `tcp.heuristics` 在 Win10 1803+ 已废弃 | 检测建议一个注定无效的动作 | 检测侧不再产出建议；动作侧 `available()` 探针剔除 |
| 5 | 回滚时非管理员报"失败"而非"权限不足" | 用户误以为备份损坏 | 回滚前提权预检，标 `SKIPPED` + 明确原因 |
| 6 | 中文 netsh 输出无冒号（`状态    关闭`） | 防火墙解析 KeyError，整项被吞成 SKIP | 正则改为"冒号可选 + 两空格分隔" |
| 7 | 中文 netsh 用词与英文直译不同 | RSS 恒显示"未知" | 按真机输出校准关键字 |
| 8 | MTU 实测抖动（1492/1492/1480） | ICMP 随机丢包被当成 MTU 上限，误报 WARN | 单包无回复重试一次 |
| 9 | 连通性单点抖动误报 | 某 CDN 节点单次慢握手被判 WARN | 改为"全部目标都慢才 WARN" |
| 10 | **时区读取用 `StandardName`** | 中文系统返回 `@tzres.dll,-572`，区域推断永远失败 | 改读 `TimeZoneKeyName` |
| 11 | **后台线程翻译导致语言切换后结果不更新** | 切语言后旧结果仍是旧语言 | 结果存 key+args，渲染时翻译 |
| 12 | UI 与 core 各有一份参数解析逻辑 | 分叉后 `profiles_parts` 一边支持，界面出现 `{profiles}` | 统一到 `core/i18n_args.py` |
| 13 | `summary_ok` 模板含占位符却未传 args | 界面显示 `{ip}/{prefix}`，比不翻译更糟 | 逐个补齐 args；无参数时才挂 key |

## 十二、已知边界

1. **必须同目录分发**（单目录打包），`LanPulse.exe` 不能单独拷走。
2. **未做代码签名**。首次运行 SmartScreen 会提示"未知发布者"，需用户点"更多信息 → 仍要运行"。
3. **VPN 网卡处理保守**。虚拟/隧道网卡不参与 DNS 与 MTU 优化，避免破坏既有 VPN 配置；代价是若 DNS 问题恰来自 VPN，工具不会自动处理。
4. **`adapter.renew_dhcp` 会导致网络中断 3-10 秒**，属预期行为，UI 已提示。
5. **协议栈重置类动作需重启才能完全生效**，UI 标"已下发，需重启"，不谎称已验证生效。
6. **切换语言后，已完成体检的详情文案保持原语言**（见 5.4），重新体检即可。
7. **区域自动识别是启发式的**，极端网络（跨国专线、海外 VPS 回国）可能判错，可在设置里手动固定。
8. **闭环测试目前只覆盖 DNS 类动作**（`dns.set_public` / `dns.flush_cache`）。
   注册表型（`proxy.reset` / `tcp.reset_stack`）、文件型（`hosts.clean_bad_lines`）、
   网络配置型（`mtu.optimize` / `adapter.renew_dhcp`）、服务型（`firewall.ensure_enabled`）
   尚未做真实闭环。建议按风险从低到高补测，`hosts.clean_bad_lines` 最后测。
9. **未测「回滚本身失败」的兜底路径**（例如备份文件被外部删除或损坏）。
   代码里有 sha256 校验会拒绝用坏备份覆盖系统，但该分支未经实测。
